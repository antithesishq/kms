# Decryption stalls after a core restarts

- **Finding name:** `decryption-stalls-after-core-restart`
- **Guarantee:** [Guarantee 2](../../../zama-kms/speedrun-report.md#guarantee-2): "Once faults stop, every core accepts connections again within 600 s, and from then a public decryption answered by all four cores succeeds within 300 s"
- **Version:** Zama KMS v0.15.0-1 before the fix: upstream [`4a644c85`](https://github.com/zama-ai/kms/commit/4a644c8546abc8b002b7e45c19bf195996e7d229) with the production changes of fix [`a51d30be`](https://github.com/zama-ai/kms/commit/a51d30beeae0131a84c9875f62de3012ae3890f9) reverted ([revert patch](../../patches/prefix/0001-revert-887-http2-keepalive.patch))
- **Summary in the report:** [the finding](../../../zama-kms/speedrun-report.md#decryption-stalls-after-core-restart)
- **The proposed fix:** [decryption-stalls-after-core-restart.patch](../../fixes/decryption-stalls-after-core-restart.patch) ([Fix](#fix))

## Symptom

The recovery check of
[`eventually_recovers_after_faults.sh`](../../../zama-kms/speedrun-tests.md#eventually_recovers_after_faults)
found every core accepting connections at once, then made three fresh public decryptions (each
requiring all four cores' answers, 90 s limit each). None finished:

```text
537.254  kms-core-client-0  [assert] Always "every core accepts client connections within 600 s after faults stop": true
537.254  kms-core-client-0  [assert] Always "public decryption answered by all four cores succeeds within 300 s
                            of every core accepting connections": false
                            {"attempts":3,"connect_wait_s":0,"decrypt_bound_s":300,"decrypt_wait_s":300,
                             "failed_attempts":3,"last_attempt":{"attempt":3,"batch":2,"connected":true,
                             "data_type":"euint128", … "exit_code":143, …}}
```

In both timelines, three cores finished each decryption session within a few milliseconds. The
core whose pod had just been killed and replaced received every request but never finished a
session. When polled for the result it answered `Unavailable` (gRPC code 14), which the server
uses for "not done yet" ([`core/service/src/engine/server.rs:112`](https://github.com/zama-ai/kms/blob/4a644c8546abc8b002b7e45c19bf195996e7d229/core/service/src/engine/server.rs#L112)), for the whole 300 s. The client
waits for all four answers, so it could not complete.

### Across both runs

Searches over all timelines of both runs, with `snouty runs search` (the event-set query interface
of the logs explorer), give these results:

- **Every failure follows a recent core restart.** All 118 failing checks in run 1 and all 41 in
  run 2 come after a pod kill or stop of a core at most 340 s before faults stopped (median 12 s).
  In 5 run-1 checks the kill landed 2 s after the fault injector's `restore`. Of the 7,737 run-1
  checks and 4,212 run-2 checks with no core killed or stopped in that window, **none failed**.
- **The core that hangs is the restarted one.** The core whose code 14 answer is the last one
  before the failure is the restarted core in 107 of 118 run-1 failures and in 41 of 41 in run 2.
  In 6 of the run-2 failures, which share one history, the restarted core is not the most recent:
  it was killed 63 s before faults stopped, during a clog, and another core was killed later.
  The other 11 run-1 failures share one history and look different: the core answering code 14
  (`kms-core-2`) had not been restarted, and the client's later attempts never reached any core.
  Those 11 are not analysed here.
- **Kills fail much more often than graceful stops.** Among checks with a core restarted in the
  340 s before faults stopped, a kill was followed by a failure 108 times out of 404 in run 1 and
  40 out of 170 in run 2, a stop 10 out of 283 and 1 out of 110.
- **The outcome is settled when the pod dies, not during recovery.** Antithesis branches each
  history many times after a kill. Of the 224 kill or stop moments that precede a check in run 1,
  none is followed by both a failing and a passing check, and 1 of 92 in run 2 is.
- **In run 2, a kill during a network fault that cuts the killed core off is the strong
  predictor:** 36 failures out of 65 such kills, against 4 out of 105 for kills without one. Run 1
  injects faults continuously, and this approximation (the latest partition and clog and their
  maximum duration) does not separate its cases: 32 out of 134 against 76 out of 270.
- **Traffic during the outage makes no difference.** In run 1, checks whose kill was followed by
  a peer core receiving a request before faults stopped failed 40 times out of 125. Checks with no
  such request failed 68 times out of 279.

## Root cause

**In plain terms.** Each core keeps one long-lived gRPC connection to each peer and sends every
MPC message of every session over it. Nothing ever checks that this connection is still alive.
There are no HTTP/2 keep-alive pings, no deadline on a send and no connect timeout. If a core
dies without its peers seeing the connection close, the peers keep the dead connection. That
happens when its pod is killed and the close does not reach them, for example because a partition
is up. The replacement pod has the same name and Service address but is not on the other end of
that connection. Every message the peers later send to the restarted core is written into the dead
connection and never answered. TCP keeps retransmitting to the vanished pod for many minutes
before it reports an error. Until then the send neither succeeds nor fails, so the retry logic
never runs and the channel never reconnects.

Public decryption runs in asynchronous mode. With four cores and threshold 1, a core can rebuild
the plaintext from its own share and two others. The three peers send each other their shares over
healthy connections and finish in milliseconds. The restarted core needs shares from two of the
three peers, and those are stuck in the dead connections. It waits for up to 900 s and answers
every result poll with "not done yet". Every new request meets the same dead connections.

**Precisely** (inferred from the code; the INFO-level logs show the effect but not the
connections):

Line numbers are those of the tested build. Files the revert doesn't touch are linked at
[`4a644c85`](https://github.com/zama-ai/kms/commit/4a644c8546abc8b002b7e45c19bf195996e7d229). In `sending_service/service.rs` and
`constants.rs`, which the revert changes, the line numbers refer to `4a644c85` with the
[revert patch](../../patches/prefix/0001-revert-887-http2-keepalive.patch) applied.

1. The peer channel is created once and reused for the life of the process.
   `connect_to_party` returns the cached client whenever one exists
   (`core/threshold-networking/src/sending_service/service.rs:79`). Every session gets its senders
   from it through `add_connections` ([`core/threshold-networking/src/grpc/manager.rs:255`](https://github.com/zama-ai/kms/blob/4a644c8546abc8b002b7e45c19bf195996e7d229/core/threshold-networking/src/grpc/manager.rs#L255)).
2. The channel has no liveness check and no time bound. The TLS endpoint is built with only
   `http2_adaptive_window` and `tcp_nodelay`
   (`core/threshold-networking/src/sending_service/service.rs:142`) and handed to `Channel::new`
   with the custom rustls connector (`core/threshold-networking/src/sending_service/service.rs:155`).
   The plaintext branch is the same (`core/threshold-networking/src/sending_service/service.rs:162`).
   Tonic only reconnects after the underlying HTTP/2 connection reports an error, and a
   half-open TCP connection reports none until the kernel gives up retransmitting.
3. The send loop waits on that connection without a deadline. `send_fn` awaits `send_value`
   (`core/threshold-networking/src/sending_service/service.rs:201`). `retry_notify`
   (`core/threshold-networking/src/sending_service/service.rs:223`) only acts when the call
   returns an error, and the backoff's `max_elapsed_time`
   (`core/threshold-networking/src/sending_service/service.rs:312`, 300 s in the deployed config)
   is checked only between failed attempts. A call that never returns is neither retried nor
   abandoned. Each peer's per-session sender task stays blocked on its first message to the
   restarted core.
4. Healthy cores finish without the restarted core, and the restarted core waits a long time.
   `NoiseFloodSmall` decryption uses an asynchronous session
   ([`core/service/src/engine/threshold/service/public_decryptor.rs:187`](https://github.com/zama-ai/kms/blob/4a644c8546abc8b002b7e45c19bf195996e7d229/core/service/src/engine/threshold/service/public_decryptor.rs#L187)). In asynchronous mode the
   robust open uses the `degree + t` bar when `degree + 3t` is not below `n`
   ([`core/threshold-execution/src/sharing/open.rs:477`](https://github.com/zama-ai/kms/blob/4a644c8546abc8b002b7e45c19bf195996e7d229/core/threshold-execution/src/sharing/open.rs#L477)–`:482`). With n = 4, t = 1 and degree 1, a
   core attempts reconstruction once it has heard from 3 parties including itself
   ([`core/threshold-execution/src/sharing/open.rs:534`](https://github.com/zama-ai/kms/blob/4a644c8546abc8b002b7e45c19bf195996e7d229/core/threshold-execution/src/sharing/open.rs#L534)–`:535`). Each receive is bounded only by the
   session's round deadline ([`core/threshold-execution/src/communication/p2p.rs:269`](https://github.com/zama-ai/kms/blob/4a644c8546abc8b002b7e45c19bf195996e7d229/core/threshold-execution/src/communication/p2p.rs#L269)), which for an
   asynchronous session is `discard_inactive_sessions_interval`
   ([`core/threshold-networking/src/sending_service/session.rs:380`](https://github.com/zama-ai/kms/blob/4a644c8546abc8b002b7e45c19bf195996e7d229/core/threshold-networking/src/sending_service/session.rs#L380), 900 s in the deployed
   `kms-server.toml`). The restarted core therefore keeps answering result polls with
   `Unavailable` ([`core/service/src/engine/server.rs:112`](https://github.com/zama-ai/kms/blob/4a644c8546abc8b002b7e45c19bf195996e7d229/core/service/src/engine/server.rs#L112)) well past the 300 s bound.

**Proven by the logs versus inferred.** The logs prove these points:
- the request reached all four cores;
- three cores finished in milliseconds;
- the restarted core neither finished nor failed for 285 s, and no core logged an error;
- this repeated for three fresh requests;
- across both runs, failures happen only after a recent restart and on the restarted core;
- the outcome is fixed at the kill.

That the peers' sends are blocked on half-open connections is inferred from the code. Send
outcomes are logged only at DEBUG, and the logs cannot show TCP state. Why some kills still let
the close reach the peers, and others do not, depends on how the environment tears the pod down.
Across run 2's timelines, a stall was much likelier when a network fault cut the killed core off at
the moment of the kill (36 failures after 65 such kills, against 4 after 105 kills without one),
although [Timeline B](#timeline-b) itself had no such fault. Run 1's data doesn't separate the two. Either way, the KMS has no mechanism to recover from a peer connection that dies
silently, and that is the defect.

## Fix

**The patch:** [decryption-stalls-after-core-restart.patch](../../fixes/decryption-stalls-after-core-restart.patch)

The patch makes every core-to-core channel detect a dead connection itself, in
`core/threshold-networking/src/sending_service/service.rs` with three new constants in
`core/threshold-networking/src/constants.rs`:

- **HTTP/2 keep-alive on both the TLS and the plaintext endpoint.**
  `http2_keep_alive_interval(10 s)`, `keep_alive_timeout(20 s)` and `keep_alive_while_idle(true)`.
  `Channel::new` applies these endpoint settings in the same way as the `http2_adaptive_window`
  setting the code already uses. A connection whose peer has vanished fails its PING within 30 s,
  and hyper closes it. Any send in flight on it fails with an error. `run_network_task` treats
  that as transient and retries, and tonic's channel reconnects to the Service address, which now
  routes to the replacement pod. Because pings are also sent while idle, a connection left dead by
  a kill is normally gone before the next session starts. That covers both analysed timelines,
  where the connections were idle at the kill.
- **A 30 s bound on establishing a connection.** For the TLS branch the custom rustls connector is
  wrapped in `tower::timeout::Timeout`, which bounds the TCP and TLS handshakes. For the plaintext
  branch it is the endpoint's `connect_timeout`. Keep-alive only covers established connections,
  and without this bound a handshake started towards an address that has just gone away can hang
  for as long as TCP retries.

This covers every case in the root cause:
- the dead connection was idle when the peer died, as in both timelines;
- it carried sends at the time;
- a new connection was being set up into the void;
- a graceful stop's close was lost in a partition.

Each now surfaces as an error within 30 s. The existing retry path delivers the message over a
fresh connection, well inside the 300 s retry budget. Nothing else changes: no new messages, no
protocol change, and a healthy connection costs one PING per peer every 10 s.

A long partition (over 30 s) now closes and reopens healthy connections too. Sends that fail on
them are retried as any transient error already is. A retried message that had in fact arrived is
handled by the existing round tagging, as it is for today's retries. The constants could later
become `CoreToCoreNetworkConfig` fields if operators need to tune them.

**How it was checked:** the patch applies cleanly to the tested source, and the build with it
(the build before the fix plus this patch) compiled on the first attempt. **Verified.** A 120-minute fix-check run with the same faults as run 1 ([`a7167532`](https://zama.antithesis.com/report/E3aRgfAZx0FG9ubZyK2gLIoR/WOfMjnEReqZRagmPUuWwUHPDAjmwjhtZw3u5U5iRSuU.html?auth=v2.public.eyJuYmYiOiIyMDI2LTEwLTE4VDA4OjA5OjE5LjE3MjY0NjYxM1oiLCJzY29wZSI6eyJSZXBvcnRTY29wZVYxIjp7ImFzc2V0IjoiV09mTWpuRVJlcVpSYWdtUFV1V3dVSFBEQWptd2podFp3M3U1VTVpUlN1VS5odG1sIiwicmVwb3J0X2lkIjoiRTNhUmdmQVp4MEZHOXViWnlLMmdMSW9SIn19feJnQdPR6ASOY1JTnB5-6WNI3-5xqJfWurzelFpKrcEWWRqdnjJ2gCtotLkMWQ5e1aqAmMFoC5nDcB466sYCTwU); [digest](../runs/fix-verify-1.md)) passed both Guarantee 2 checks in all 6,934 attempts, and both of its Sometimes markers were hit: a core the client couldn't reach after faults stopped came back 87 times, and a decryption that needed a retry after faults stopped then succeeded 116 times. Before the fix, 118 of 8,424 checks (1.4 %) failed in the run with the same faults, so about 97 failures would have been expected in 6,934 checks; none occurred.

## Comparison with upstream

The upstream fix is [`a51d30be`](https://github.com/zama-ai/kms/commit/a51d30beeae0131a84c9875f62de3012ae3890f9),
"fix: detect dead peer connections with HTTP/2 keepalive" ([PR #887](https://github.com/zama-ai/kms/pull/887),
merged 2026-09-25). The analysis above was written without it: the source had no history, the
fix's own tests were removed from the copy, and the inputs named neither the fix nor the issue.

**Verdict: same.** Same mechanism and an equivalent fix. Upstream's description of the bug: a
running party could not reach a restarted one over a dead connection, because nothing detected
that the connection had died. Both fixes add HTTP/2 keep-alive pings, sent also while idle, to both
the TLS and the plaintext channel builder in `sending_service/service.rs`, so that a dead
connection fails, the existing retry resends, and tonic reconnects.

Differences:
- **Values and configurability.** Upstream uses a 15 s interval and a 30 s timeout, exposed as
  `keepalive_interval_secs` / `keepalive_timeout_secs` in the core-to-core network configuration
  with validation. The proposed patch uses fixed constants of 10 s and 20 s.
- **Retry budget.** Upstream raises the default `MAX_ELAPSED_TIME` from 60 s to 90 s and checks that
  it exceeds keep-alive interval plus timeout, so a send is still being retried when the
  keep-alive closes the dead connection. The proposed patch fits inside the existing 60 s default
  (10 s + 20 s = 30 s) but doesn't enforce the relation.
- **Connect timeout.** The proposed patch also bounds connection setup at 30 s (a
  `tower::timeout::Timeout` around the TLS connector, and `connect_timeout` on the plaintext
  branch). Upstream has no such bound. It's an addition, not a disagreement.
- **Where the restarted core waits.** The analysis attributes the restarted core's long wait to the
  asynchronous session's round deadline (`discard_inactive_sessions_interval`, 900 s). Upstream's
  description doesn't go into this, so there's nothing to compare.

**Caveat.** The blinding was procedural. The upstream fix was merged in September 2026, after the
model's training data was collected, so it can't have been recalled. But half-open connections and
gRPC keep-alive are a well-known pattern, and the model may know it from elsewhere.
