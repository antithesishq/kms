- Evidence: [iterate-2](runs/iterate-2.md): kms-core-2-core-2, a fresh pod after a pod kill at vtime 247.24, starts reading `PRIV-p2/FheKeyInfo/…` while partitions separate it from MinIO, then exits 1 with "reading failed for FheKeyInfo … Unencrypted load failed: streaming error" (vtime 261.57). Kubernetes restarts the container, and the core rejoins: Guarantee 2's reconnect and decrypt checks passed in all 1145 examples. Log link: [log][core-exit-1]

- Fix: none to the SUT or workload (a restart wrapper around kms-server would be harness intervention). Recorded as a recurring warning; Guarantee 2's window already allows for the restart back-off.
- Re-run: n/a

<a id="boot-panic-port-in-use"></a>
## A restarting core panics because its service port is already bound · iterate-3 · No unexpected container exits (kms-core, exit 101) · suspect
- Evidence: [iterate-3](runs/iterate-3.md): kms-core-2-core-2 at vtime 1123.32 panics at `core/service/src/bin/kms-server.rs:594`: "Could not bind to 0.0.0.0:50100 … AddrInUse". It is a fresh container 14.8 s into boot, after a run of boot failures ("reading failed for FheKeyInfo … streaming error") while partitions cut it off from MinIO. 3 counterexamples in iterate-3; none in iterate-2 or iterate-4. Log link: [log][boot-panic-1]
- Checklist hit: 3 (configuration/topology) can't be ruled out: nothing in the manifests shares the pod's port 50100 (no hostNetwork, no other container listening), and the log doesn't show what held the port.
- Probes: [probe file](probes/boot-panic-port-in-use.md). The run had ended, so no probe ran inside it. Ruled out from code, logs and the manifest: a leftover server process, another container on the port, and kms-server binding the port twice. Still open, and consistent with everything seen: an ephemeral-port collision. 50100 lies inside Linux's default ephemeral range (32768–60999), and about 90 outgoing S3 connections from the pod's network namespace in the 75 s before the bind could leave a client socket on local port 50100.
- Fix: none to the harness. If it recurs in a live run, probe the pod's sockets just before the bind. Reported as a lead (unconfirmed), not a finding.
- Re-run: watch the hunts
- **Update after the hunts (2026-10-18):** it recurred in [hunt-current-2](runs/hunt-current-2.md#exit-101-what-was-happening): 150 exit counterexamples, 129 bind panics, all on kms-core-1, in three clusters (1101–1160, 1574, 1619–1637). The first comes 2.25 s after a pod stop, with no network fault or clock jump active and 7.0 GiB free. In one history the port stays taken across four kms-server processes in a row in the same pod (at least 42.6 s, no other container running); in a sibling history the bind works again about 76 s after the stop. No log line shows the holder. Not seen in hunt-current-1 or either pre-fix hunt.
- **Local check of the leading mechanism** ([tw-bind-check.md](probes/boot-panic-port-in-use/tw-bind-check.md)): in a private network namespace on this VM (Linux 6.12), an outgoing connection whose kernel-chosen local port is 50100, closed by the client first, leaves a TIME-WAIT socket on 50100, and `bind(0.0.0.0:50100)` with `SO_REUSEADDR` (what tokio's `TcpListener::bind` does) then fails with `EADDRINUSE` until it expires (60 s on Linux). That matches a port that stays taken for 34–43 s across restarts and frees within about a minute. The chart's production port is also 50100 ([values.yaml](../../charts/kms-core/values.yaml), `client: 50100`), inside Linux's default ephemeral range 32768–60999. Still unconfirmed in the run itself: no socket listing exists for the failing moment.
- Classification stays **suspect**: reported as an unconfirmed finding, not a confirmed one.

<a id="prefix-recovery-fails-after-core-restart"></a>
## On the pre-fix build, a restarted core never finishes its part of new decryptions · hunt-prefix-1, hunt-prefix-2 · Guarantee 2 "public decryption answered by all four cores succeeds within 300 s of every core accepting connections" · real (expected on the pre-fix build)
- Evidence: [hunt-prefix-1](runs/hunt-prefix-1.md) (118 counterexamples, first at vtime 537.25) and [hunt-prefix-2](runs/hunt-prefix-2.md) (41, first at vtime 542.35). In both first timelines a core's pod is killed (kms-core-1 at 235.13 during a partition that isolated kms-core-3; kms-core-4 at 238.15 with no network fault), faults stop 2–4 s later, the replacement core is up and every core accepts connections at once, and then for 300 s the other three cores finish every decryption session in milliseconds while the restarted core answers every result poll with code 14 ("not done yet").
- Checklist: (1) client use: the `-a` decryption is the documented way to require every party's response; a 90 s per-attempt timeout with retries for 300 s is generous next to the 3–40 ms the healthy cores take. (2) assumption: the property's 300 s window is inferred, not documented, but the current version passes the same check in [hunt-current-1](runs/hunt-current-1.md) and [hunt-current-2](runs/hunt-current-2.md) under the same faults, so it's achievable. (3) configuration: identical manifests and workload on both builds ([same-workload.txt](logs/same-workload.txt)); network_timeout 300 s is the chart's value. (4) no scripted fault: the pod kill came from Antithesis's fault injector. (5) checker: the window starts only after every core accepts connections, and the failure is the restarted core's missing answer, which the logs show directly.
- Classification: real, and its signature matches the [expected symptom](positive-control.md) in substance: the restarted core is the missing response, the other three answer at once, Guarantee 1 holds, and the current version passes. Two predicted lines can't appear in these timelines: the CLI's own error (the script's 90 s per-attempt timeout ends the CLI while the restarted core holds each call for 60 s), and the restarted core's "(Share reconstruction) Some party has timed out" (due at about vtime 552–560, after the failure). A search of hunt-prefix-1 finds that line 40 times on kms-core-2 in other timelines. The kill-only trigger in hunt-prefix-2 was anticipated in positive-control.md.
- Fix: none (this is the known bug). Not counted against green.

<a id="peak-memory-command-backlog"></a>
## Memory use passes 95 % of the test VM while hundreds of test commands are waiting · hunt-current-1, hunt-current-2, hunt-prefix-1, hunt-prefix-2 · Antithesis default "Peak memory usage" · false-positive (test VM too small for the harness's command backlog)
- Evidence: failing in all four 4-hour hunts (current 1235 and 615 counterexamples; pre-fix 1650 and 1370), never in the 30-minute runs. Investigation in [hunt-current-2](runs/hunt-current-2.md#peak-memory-what-was-happening): the test VM has 9.71 GiB ("Total memory: 10431954944 bytes" at every kms-server boot), so the threshold is about 9.23 GiB. Both first counterexamples (vtime 733.60 and 801.69) come long after setup, when 183–316 test commands are running at once in the client pod (209 public and 20 user decryptions waiting on `timeout 300` attempts, 54–161 open reshares) and 26–31 reshare requests reach each core within 20 s. MinIO and coredns restart or stall just before, without a fault aimed at them. In a sibling history where about 200 waiting decryptions finish at 807–810, cores booting later see 6.2–7.0 GiB free again. The peak value itself isn't readable through the API.
- Checklist hit: 3 (resource limits): the manifests' memory limits add up to 37 GiB against a 9.71 GiB VM, and the workload lets the composer pile up hundreds of concurrent commands, each a `kms-core-client` process, plus many concurrent reshares, during long fault windows. That load is the harness's, not an operator's.
- Not ruled out: part of the memory held by the cores could stay held without the backlog (a leak). The logs don't show which process holds it.
- Test: [hunt-current-4](runs/hunt-current-4.md) runs the same faults with a 16 GiB test VM (`custom.vm_memory_mb=16384`). If the property passes there, it's headroom for the backlog; if memory keeps climbing to 95 % of 16 GiB, it's worth a leak investigation.
- Result: [hunt-current-4](runs/hunt-current-4.md#peak-memory-usage) passes "Peak memory usage" with 16 GiB: 126,556 evaluations, 0 failing, against 1,235 failing in [hunt-current-1](runs/hunt-current-1.md) with the same level-3 faults at 9.71 GiB. The run was 105 minutes against 240, but it evaluated the property more often than hunt-current-1. So the failure is the test VM's size against the backlog (checklist 3), not memory growing without bound. A slow leak isn't ruled out: the property doesn't expose its peak value, so how close the 16 GiB run came to 95 % is unknown.
- Later runs: it also fails at 9.71 GiB in the fix check (12), [hunt-current-5](runs/hunt-current-5.md) (1) and [hunt-current-7](runs/hunt-current-7.md) (331), not in [hunt-current-3](runs/hunt-current-3.md), and passes in the second 16 GiB run, [hunt-current-6](runs/hunt-current-6.md) (125 minutes, timing fuzzing).
- Fix: none applied during the hunt (changing the workload now would break the comparison with the pre-fix runs). For future runs: cap concurrent test commands and reshares in the workload, or give the test VM more memory.

## A storage error while a core boots leaves it in recovery mode · hunt-current-3 · "public decryption answered by all four cores succeeds within 300 s of every core accepting connections" (Guarantee 2) · real
- Evidence: execution A of the checker, first counterexample at vtime 1405.556 (input_hash -7353950694920754647), [digest](runs/hunt-current-3.md#failing-public-decryption-answered-by-all-four-cores-succeeds-within-300-s-of-every-core-accepting-connections), log [hunt-current-3-g2decrypt-7353950694920754647.ndjson](logs/hunt-current-3-g2decrypt-7353950694920754647.ndjson). kms-core-2 logs "Failed to read SigningKey … dispatch failure" at 1089.59 during a MinIO partition, then "SIGNING KEY NOT AVAILABLE, ENTERING RECOVERY MODE!!!!" at 1089.64. After faults stop it accepts connections but refuses all 27 decryptions with "Signing key is not present … booted in recovery mode" (gRPC code 9) for 300 s, with no restart. Write-up: [violations/storage-error-enters-recovery-mode.md](violations/storage-error-enters-recovery-mode.md).
- Checklist hit: clean.
  1. Client use: the checker connects to all four cores, which accept connections; the refusal is the server's own, by design of recovery mode, not a client error.
  2. Assumption: the docs say a restarted node reuses the material it finds on disk to rejoin; the key was on storage, and the read failed transiently. The property needs all four cores, as written in Guarantee 2.
  3. Configuration: default storage settings; the partition is an ordinary Antithesis network fault, and it ended 1100.67, before the checker's window.
  4. Scripted failure: none; the checker only sends client requests after `ANTITHESIS_STOP_FAULTS`.
  5. Checker: it reports exactly what the core returned.
- Same entry into recovery mode in [hunt-current-1](runs/hunt-current-1.md) at vtime 912.49 on kms-core-1, where no request reached the core afterwards.
- Next: adversarial check ([adversarial/storage-error-enters-recovery-mode.md](adversarial/storage-error-enters-recovery-mode.md)).

  - Faults pause at 1196.59. kms-core-2's pod stops at 1225.20 and is back at 1235.06. The launcher documents this: "a graceful stop that started just before the window can even land inside it, up to the pod's termination grace period later" ([advanced_k8s_test.md](../../advanced_k8s_test.md)), and the checker allows for it by timing the decryption bound from when all four cores accept connections. Attempt 1 fails to connect to party 2 at 1235.69 ("Network is unreachable").
  - Attempt 2 starts at 1245.77. The client's next lines come at 1533.02: it has read the public key from storage and is still encrypting the plaintext locally, then it is "Terminated" (exit 143). It never sent a request to any core.
  - The whole history logs 0–6 events per 10 s from 1240 to 1570, against 300–400 just before. - Fix: none to the harness. The two later timing-fuzzing runs ([hunt-current-6](runs/hunt-current-6.md), [hunt-current-7](runs/hunt-current-7.md)) had no stall and passed Guarantee 2 throughout.
