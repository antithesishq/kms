# Positive control: restarted peer unreachable over a dead connection

- **Public reference:** [PR #887](https://github.com/zama-ai/kms/pull/887), "fix: detect dead peer connections with HTTP/2 keepalive". The PR shows public decryption failing in Zama's own rolling-upgrade CI ("public decrypt fails, `Only got 5/13`", run [35920478407](https://github.com/zama-ai/kms/actions/runs/35920478407)) and passing with the fix. The linked analysis issue is in the private `kms-internal` repository. The brief's entry is in [system-brief.md](system-brief.md#known-bugs-and-fixes).
- **Violates:** [Guarantee 2](guarantees.md#guarantee-2), "Once faults stop, every core accepts connections again within 600 s, and from then on a new public decryption answered by all four cores succeeds within 300 s, so a core that was killed or cut off has rejoined (availability after recovery, i.e. guaranteed output delivery)" (as corrected on 2026-10-17, see [speedrun-log.md](speedrun-log.md))
- **Trigger:** a core's pod is deleted (pod_kill, or a pod_stop that ends in a kill) while a network fault cuts its link to a running core, so the running core never sees its cached core-to-core connection close. The replacement pod comes up under a new IP, and the running core keeps sending into the dead HTTP/2 connection. Without keepalive, the kernel aborts that connection only about 15 minutes after its first unacknowledged send.
- **Expected symptom:** after faults stop, every Guarantee 2 attempt (a fresh public decryption with `-a`, which needs all four responses) fails for more than 300 s. The CLI reports `Only got 3/4 public decryption responses, need at least 4`, or a poll timeout for one core. The missing response is the restarted core's. Its decryption session waits the full `network_timeout` (300 s in the [harness config](../config/manifests/31-kms-core-1.yaml)) for the share of the running core whose connection is dead, so its log is expected to show `(Share reconstruction) Some party has timed out`. The other three cores answer at once with the correct plaintext, so [Guarantee 1](guarantees.md#guarantee-1) still holds. The cluster recovers without operator action about 15 minutes after the dead connection's first unacknowledged send. On the fixed build, keepalive closes the dead connection within 45 s (15 s interval, 30 s timeout), and the same check passes.
- **Refs:** `prefix_ref` = `612207a9567702dd7251eaac3c812d250220880f` (fix^, the historical pre-fix commit; the pre-fix build is `current_ref` with the fix reverted, see "Build"), `fix_ref` = `a51d30beeae0131a84c9875f62de3012ae3890f9` ([commit](https://github.com/zama-ai/kms/commit/a51d30beeae0131a84c9875f62de3012ae3890f9), squash merge of [PR #887](https://github.com/zama-ai/kms/pull/887), 2026-09-25)
- **Affected releases:** v0.14.x (the PR: "Since v0.14, an enclave party's TCP connections end inside the enclave"; "v0.14 parties do not get this fix"), and every `main` commit before 2026-09-25, which has no peer keepalive. The fix ships after v0.14.
- **Build:** ok, 2026-10-17. Current harness commit `3095d82a` plus [the revert patch](../patches/prefix/0001-revert-887-http2-keepalive.patch) (production hunks of `a51d30be` reversed), built with the same `antithesis/images/build.sh` and Rust 1.98.1 as current, tagged `speedrun-3095d82a-prefix887`. The pre-fix `kms-server` has no `keepalive_interval_secs` / `get_keepalive_timeout` symbols; the current one has both. Log: [build-prefix-887.txt](logs/build-prefix-887.txt)

## Why the fix is reverted on current

- **The production hunks reverse-apply cleanly.** `git show a51d30be -- core/service core/threshold-networking/src/constants.rs core/threshold-networking/src/grpc/config.rs core/threshold-networking/src/sending_service/service.rs | git apply -R --check` exits 0 on the working tree (`HEAD` 3095d82a). The whole commit does not apply (`patch failed: core/threshold-networking/src/sending_service/session.rs:671`). Every `session.rs` hunk of the fix is inside `#[cfg(test)] mod tests`: the restart tests and their `FreezingProxy`. They conflict only with the later `Vec<u8>` to `Bytes` refactor ([#893](https://github.com/zama-ai/kms/commit/563548a1b08d71f08b42169508299c74e884ea98)). The small adjustment is to delete the two added tests, the proxy, and the two `keepalive_*` lines in a test config by hand. Otherwise `cargo test -p threshold-networking` does not compile. The image build compiles no tests, so it is not affected either way.
- **The reverted code matches the pre-fix code on the bug's path.** After the revert, `connect_to_party` in `sending_service/service.rs` is identical to fix^ (the channel builder again has only `http2_adaptive_window` and `tcp_nodelay`). The send loop `run_network_task` differs from fix^ only in the message type (`Bytes`, #893). No later commit adds another keepalive, a client request timeout or a channel reset: `git grep` finds no `keepalive_*` reference outside the files the fix touched. The harness config sets `max_elapsed_time = 300` explicitly, so the fix's change of the `MAX_ELAPSED_TIME` default (60 s to 90 s) has no effect, and it sets no `keepalive_*` field, so the revert does not break config parsing.
- **It isolates one fix and reuses the build cache.** fix^ is only 18 commits behind `current_ref`, but an old-release build would still need the instrumentation shim ported (`Cargo.toml` and `observability/` changed in 3 files since fix^) and a second full build. The revert recompiles only `threshold-networking`, `kms` and their dependents in the shared target cache.

## Fault needs

Both fault types are in the default `custom.enabled_faults` of `advanced_k8s_test` (`network,pod_stop,pod_kill,clock_jitter`), so no fault type is missing.

- **pod_kill on a core** (immediate delete, the StatefulSet reschedules it). pod_stop works too when the graceful stop runs out its grace period.
- **network faults** (partition, packet loss) on the link between that core and a running core, overlapping the deletion, so the connection close does not reach the running core.

Risk: in this harness, a killed pod normally closes its connections. The trigger therefore depends on the deletion and a network fault overlapping, and on the old flow staying routed to the dead pod IP after the partition heals. The PR's own test models exactly this with a frozen TCP proxy. If Antithesis's pod deletion itself drops the closing packets, the trigger is more frequent. Expected time to trigger: hours of fault injection rather than minutes, because a deletion must overlap a network fault on one of that core's links. The dead connection must also still be open when faults stop, which happens if the deletion was less than about 10 minutes before the quiet period.

## Criteria

| | Criterion | Evidence |
|---|---|---|
| a | Violates a T2 guarantee | [Guarantee 2](guarantees.md#guarantee-2) requires that a fresh public decryption answered by all four cores succeeds within 300 s after faults stop. With the bug, the restarted core cannot get shares from a running peer for about 15 minutes, and every session it starts waits 300 s for them, so no attempt can succeed in the window. The PR shows the same symptom in production-like CI: "the restarted parties then do not get enough shares, and public decryption fails". |
| b | Needs faults/concurrency | A restart of one party (pod deletion) whose old connection the peer does not see close. A single-process unit test does not catch it: the PR needed a two-party test with a freezing TCP proxy. |
| c | Public and recognizable | [PR #887](https://github.com/zama-ai/kms/pull/887) is public, with a full description and links to the failing and passing CI runs. The commit exists upstream (`GET /repos/zama-ai/kms/commits/a51d30be…` returns 200). It is three weeks older than `current_ref` and comes from Zama's v0.14 to v0.15 upgrade work, so Zama's engineers know it. |
| d | Cheap to build | Revert on current: the production hunks dry-run clean, with only a small test-only adjustment. It uses the current toolchain, the current `Cargo.lock` and the shared cargo target cache. |

## Considered and not used

- Lowering the harness's `network_timeout` (300 s), or setting `keepalive_*` values, to widen the window: bug-specific tuning.
- Excluding MinIO and the client pod from pod faults so that more deletions land on cores: a topology choice made for this bug's preconditions.
- A workload step that kills or partitions a core: orchestration, and a fault mechanism outside the client API. The control is checked only by the general Guarantee 2 check, which runs the same way on both builds.

## Other candidates considered

- **Failed reshare deletes public keys** ([PR #792](https://github.com/zama-ai/kms/pull/792), [00cebe09](https://github.com/zama-ai/kms/commit/00cebe099c99464d613d5835a0c9416334ab23c8)): passes a to c on paper. It breaks [Guarantee 3](guarantees.md#guarantee-3), because before the fix the rollback after a storage failure in `store_reshared_keys` called `purge_fhe_keys`, which deletes the key's `PublicKey`, `ServerKey` and `CompressedXofKeySet` from public storage. The trigger is reachable: a MinIO write fails during a reshare's storage phase, under a network fault or a MinIO deletion. It ranks second for two reasons. First, the trigger window (the storage phase of a reshare) is short, so it is likely rarer than #887. Second, the revert does not apply (`epoch_manager.rs`, the proto and `ARCHITECTURE.md` conflict, and [#873](https://github.com/zama-ai/kms/commit/b0ae82774789c5728c91c00a6fcab909d8d82b29) rewrote the same rollback later). So it needs the old release, 92 commits behind, with the instrumentation shim ported (`Cargo.toml`/`observability` changed by 72+/60- lines since). The PR's discussion link is a private Slack thread.
- **Network deadlock** ([PR #658](https://github.com/zama-ai/kms/pull/658), [50595343](https://github.com/zama-ai/kms/commit/5059534364cc27f190967c8644a7f5265130e415)): it breaks [Guarantee 2](guarantees.md#guarantee-2) (a deadlocked core never answers again), and its trigger is a race (a `DashMap` shard guard held across an `.await` in the cleaning task). It was not chosen because the revert is impossible (the files moved, and [#834](https://github.com/zama-ai/kms/commit/715382023483e78fbadc2e6b43093792f33e0a53) removed the field later). The old release is 182 commits behind and also carries #887's bug, so a Guarantee 2 failure there could not be attributed to one bug.
- **Network message dropped** ([PR #624](https://github.com/zama-ai/kms/pull/624), [3f6ebcdf](https://github.com/zama-ai/kms/commit/3f6ebcdf756bc0c8af67a66a26c7490acf581fda)): fails (a) as written. One dropped message makes the receiver count its sender as timed out after `network_timeout`, and the robust opening still reconstructs with `t = 1`. So it delays one session but does not reliably break a guarantee, and the race must also happen inside the recovery window. The revert is impossible (`sending_service.rs` no longer exists), and the old release is 206 commits behind.
- **User decryption returned 0** ([e3c79fa7](https://github.com/zama-ai/kms/commit/e3c79fa7299d84ac5aeb59c19d944ad4c4413e47), PR #2552 of the earlier `kms-core` repository): fails (b), (c) and (d). It would break [Guarantee 4](guarantees.md#guarantee-4), but only when every signcrypted share fails validation, which needs malicious or corrupt responses, not crashes or partitions. `https://github.com/zama-ai/kms/pull/2552` does not exist (the API returns 404), and only the commit is public. It is 755 commits behind and predates the epochs that the harness's `kms-init` creates, and the revert conflicts in 7 files.
- **Idle but active sessions evicted** ([PR #834](https://github.com/zama-ai/kms/pull/834), [71538202](https://github.com/zama-ai/kms/commit/715382023483e78fbadc2e6b43093792f33e0a53)): the revert applies cleanly, but it fails (a). Eviction needs an active session with no received message for `discard_inactive_sessions_interval` (900 s in the harness config), measured on the monotonic clock, so clock jumps do not shorten it. A decryption has 1 or 2 rounds, each bounded by the 300 s `network_timeout`, and the other parties keep sending, so it never gets there. Long sessions (key generation, reshare) could get there, but key generation is in no guarantee, and a reshare that fails while the earlier epoch keeps serving is allowed by [Guarantee 3](guarantees.md#guarantee-3). The PR's issue link is private (`kms-internal`).
